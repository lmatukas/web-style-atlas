## Reproduce from a fresh clone

Use Node 24.19.0 and the committed lockfile. No secrets or paid services needed.

```sh
git clone https://github.com/lmatukas/web-style-atlas.git
cd web-style-atlas
npm ci --ignore-scripts --no-audit --no-fund
node scripts/ci-scope.mjs --full
node scripts/ci.mjs validate
npm run check
npx playwright install --with-deps --only-shell chromium
node scripts/ci.mjs browser
git diff --exit-code
npm run dev -- --base /web-style-atlas/
```

Open the local URL printed by the server. The full browser suite checks all
references at 360/768/1440, gallery controls, nested paths and renderer failures.
No PNG regeneration is needed when their source hashes remain current. The
version bump required a fresh canonical render of all 48 release previews.

## Repeat publication when authorized

The owner enabled Pages and dispatched the prepared workflow with publication
authorized. Both verify and deploy succeeded; the actual gallery and reference
page were opened afterward. The workflow remains manual: it never runs on a
push, PR or schedule. Later catalogue changes require a new authorized dispatch;
the release version/count gate must be updated for a later release.

1. After the implementation PR is merged, open repository **Settings → Pages**
   and choose **GitHub Actions** as the build/deployment source. This step needs
   repository administration permission; a connected app's content-write access
   does not imply Pages administration access.
2. Open **Actions → Verify release and optionally publish Pages → Run workflow**.
   Select **main**. Leave `publish` false for verification only. Set it true only
   when public gallery publication is authorized. Other branch dispatches do not
   run the release job. Failed gates prevent upload and deployment.
3. Open the actual URL returned by the `github-pages` environment. Check all
   twelve cards, search/reset, compare three, B/mobile and prompt copy. Open a
   card's actual reference link and ensure its styles and images load. Record
   that real URL and opened example in release evidence; a green log alone does
   not complete publication. Do not infer the URL from the repository name.
4. If a tagged GitHub release is desired, tag the verified merged implementation
   revision `v0.1.0` and use CHANGELOG.md as release notes. Keep later tracking
   commits separate. Re-run verification if source changes before publication.

The workflow uploads only `dist` with one-day retention after successful full
checks and only when publication is selected. No dependency cache, video or
successful test-report artifacts are uploaded. Concurrent release jobs queue;
an active deployment is never cancelled by a newer dispatch.
